# JobPilot V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 本项目推荐同一会话顺序实施，便于用户边做边学。

**Goal:** 交付真实模型驱动的求职辅助 Agent，支持受限详情查询、证据匹配、人工审核和跨进程恢复。

**Architecture:** 在现有 TypeScript 工程中新增独立 jobpilot 模块，以一个岗位一个 LangGraph thread 的方式串行处理批次。模型与本地岗位工具通过接口注入；图检查点和业务结果分别存储。保留现有浏览器和发送流程，V1 不连接它们。

**Tech Stack:** Node 24、TypeScript/ESM、LangGraph JS、Zod、兼容模型 SDK、官方 SQLite checkpointer、Node SQLite、Vitest。精确依赖版本在任务 1 按官方文档和 Node 24 实测锁定。

**Spec:** [已确认设计](../specs/2026-11-01-jobpilot-langgraph-design.md)。实施前同时阅读本计划、设计和根目录 AGENTS.md。

**Status:** 用户已选择主代理顺序实施、分阶段讲解、最后统一审查。V1 代码与 CLI 已实现；独立审查 6 个重要问题均经失败回归测试修复；最终 47 文件/177 项测试通过。任务 9 的人类语义复核与用户练习未完成，次要测试/遥测差距见 docs/jobpilot/acceptance.md。下方为原始实施清单，实际执行证据以 implementation-log.md 和本计划 ledger 为准。

## Global Constraints

- 工作目录：D:/code/job-search-skills；新增入口 `scripts/boss.cmd jobpilot ...`，沿用 Node 24，现有命令语义不变。
- V1 只接受 UTF-8 txt/md 简历与 JSON 岗位/偏好；单用户、单批最多 10 岗位、岗位串行运行。
- 每岗位 decide 最多 3 轮，详情读取最多 2 次尝试；成功同版本不重复读取。
- 每岗位实际模型请求累计最多 12 次，含重试、格式修复和修改；共享简历提取单独最多 2 次。
- 用户要求修改最多 2 轮；达到上限后仍可接受或拒绝当前草稿，不能继续生成。
- 模型单次超时 45 秒；工具单次 15 秒；每岗位累计活跃执行时间最多 180 秒，人工等待不计入，重启不重置预算。
- 每个逻辑操作最多 2 次实际请求；临时网络故障最多重试 1 次；结构不合法最多修复 1 次；所有重试共享同一上限。
- 简历 20,000 字符、单岗位详情 20,000 字符、修改意见 2,000 字符，超限报错。字符计数统一使用 Unicode code point；UTF-8 解码失败拒绝。
- checkpoint：data/jobpilot/checkpoints.sqlite；业务数据：data/jobpilot/app.sqlite；冻结输入：private/jobpilot/inputs；报告：output/jobpilot。不同于现有投递数据库。
- 只使用虚构材料开发和演示；真实模型验收与单元测试分开，无配置时明确报告未验收，不把 mock 结果称为真实结果。
- 不发送消息、不投递、不启动浏览器、不复制其他项目密钥、不初始化 Git、不改变私人材料和历史投递记录。
- 当前不是 Git 仓库，每任务记录文件和验证结果到 docs/jobpilot/implementation-log.md，替代提交检查点；未来已成为仓库时再按当前授权提交。
- V1.1 的 MCP 真实导入单独制定后续计划；本计划不把尚未完成的集成列为 V1 成果。

## Review Focus

1. 输入被用户编辑、Windows 路径含中文空格：按内容冻结快照，恢复继续旧输入，新的输入创建新批次（任务 2、7）。
2. 多工具调用、坏参数和 JD 内指令：不能访问其他岗位或执行额外工具，仍受同一计数器限制（任务 5）。
3. 模型临时失败后又返回坏 JSON：重试机制不能叠加突破每操作 2 次和每岗位 12 次（任务 3、4）。
4. 审核已写入但进程在恢复途中崩溃：重放同 reviewId 不会重复修改，旧版本不能覆盖新草稿（任务 6、7）。
5. 单批一个任务暂停、另一个失败：其他岗位正常推进；恢复不重跑共享简历提取（任务 7、8）。

## Task 2：定义输入输出与可追溯本地岗位工具

**Files:** 新建 schemas.ts、types.ts、inputs.ts、evidence.ts、tools/local-jobs.ts；测试 inputs.test.ts、local-jobs.test.ts；虚构输入放 tests/fixtures/jobpilot/demo/。

**Interfaces:**
- schemas.ts 使用 Zod 定义并导出以下 schema，types.ts 从 schema 推导类型，避免两套声明漂移。
- `ResumeDocument = {text, hash, evidence: Evidence[]}`；`Evidence = {id, source: 'resume'|'job', text, sourceHash}`。
- `Preferences = {targetRoles: string[], preferredCities: string[], hardConstraints: {cities?: string[], minMonthlySalaryCny?: number}}`；未设硬约束不自动排除岗位，薪资范围不明确时记 unknown。
- `JobSummary = {jobId,title,company,city?,salary?,url?,source,capturedAt}`；`JobDetail = {jobId,description,requirements?: string[],hash,evidence: Evidence[],source,capturedAt}`。
- `JobBundle = {schemaVersion: 1, summaries: JobSummary[], details: JobDetailInput[], initialDetailIds: string[]}`。JobDetailInput 是 JobDetail 去掉 hash/evidence 的输入形态；details 不进入模型上下文，initialDetailIds 指定哪些正文在开局已可见，其他详情只能经工具取得。
- `Analysis = {recommendation, requirements, matches, gaps, unknowns, rationale}`，recommendation 固定设计中四种枚举；每条 requirement 有 requirementId、text、priority、jobEvidenceIds；match 有 requirementId、resumeEvidenceIds、reason；gap 有 requirementId、reason；unknowns 为字符串数组。
- `Draft = {text: string, evidenceIds: string[]}`；`ReviewRequest = {reviewId,threadId,draftVersion,decision: 'approve'|'revise'|'reject',feedback?: string}`。
- `loadInputs(paths: {resume:string;jobs:string;preferences:string}): Promise<ValidatedInputs>`；ValidatedInputs 包含上述三类输入及来源模式 local。
- `freezeInputs(root: string, input: ValidatedInputs): Promise<InputSnapshot>`；InputSnapshot 包含文件路径、三类内容哈希和 schemaVersion，只增不覆盖。
- `LocalJobSource.listJobs(): Promise<JobSummary[]>`；`getJobDetail(jobId: string): Promise<DetailObservation>`；DetailObservation 为 `{status:'ok',detail}` 或 `{status:'not_found'|'unavailable',message}`。
- `validateEvidence(analysis: Analysis, draft: Draft|undefined, evidence: Evidence[]): void` 检查 ID 存在、归属和引用文字；语义正确性留给评估。

## Task 3：业务数据库、操作缓存与持久化预算

**Files:** 新建 store.ts、budget.ts；新增 store.test.ts、budget.test.ts。复用 src/run-lock.ts，不改旧数据库。

**Interfaces:**
- `openJobpilotStore(file: string): JobpilotStore`；`close(): void`。
- 表：batches(batch_id PK, snapshot_json, profile_json, status)；tasks(thread_id PK, batch_id, job_id, status, schema_version)；results(thread_id,draft_version 联合 PK,result_json)；reviews(review_id PK,thread_id,payload_hash,status,response_json)；model_operations(operation_id PK,scope_id,input_hash,status,response_json)；budgets(scope_id PK,model_attempts,tool_attempts,decision_turns,active_ms,revision_count)。使用事务、唯一键与 WAL，完整列/索引由实现者按上述契约补齐。
- `store.reserveAttempt(scopeId: string, kind: 'model'|'tool', operationId: string): void` 原子扣预算；操作最多 2 次，单岗位总数按默认限额。
- `store.getOperation(operationId: string): unknown|undefined`；`store.completeOperation(operationId: string, response: unknown): void`。
- `store.chargeActive(scopeId: string, ms: number): void`；`store.incrementDecision(scopeId: string): void`；`store.incrementRevision(scopeId: string): void`。
- `store.saveResult(result: JobResult): void`；JobResult 在 types.ts 定义，包含 threadId、batchId、jobId、draftVersion、taskStatus、analysis?、draft?、review?、error?、provenance。
- `store.reserveReview(request: ReviewRequest): 'new'|'pending'|'completed'`；`store.completeReview(reviewId: string, result: JobResult): void`；同 ID 不同 payload 拒绝，response 可取回。
- `withBudget<T>(scopeId: string, operationId: string, kind: 'model'|'tool', call: (signal: AbortSignal)=>Promise<T>): Promise<T>` 由 factory 注入 store、clock、limits；请求前预留预算，使用可取消超时。崩溃恢复时对未完成预留按该次超时额度保守计入 active_ms，不让重启刷新时间预算。

- [ ] 写断言：第 13 次模型请求不调用 provider；第 3 次工具尝试拒绝；重开 DB 计数不变；重复 saveResult 行数为 1；重复审核相同 payload 返回原状态、不同 payload 报错；缓存命中不再扣新请求。
- [ ] 写失败窗口测试：先扣预算再模拟崩溃，重开后预算仍被扣；未完成请求的活跃耗时不被清零；人工等待一小时不增加 active_ms（使用假时钟）。
- [ ] 运行 store/budget 测试确认失败，再实现数据库和预算调度；不要在写事务内等待网络。
- [ ] 重跑测试、typecheck 并记录。学习练习：说明“检查点保存状态”为什么不能自动防止重复写结果或重复计费。

## Task 6：人工审核、修改与磁盘恢复
