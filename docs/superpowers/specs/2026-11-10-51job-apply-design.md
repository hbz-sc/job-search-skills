## 方案比较与选择

1. 两个独立项目：隔离彻底，但重复维护简历配置、日志、去重、恢复与依赖。用户没有独立部署需求。
2. 同一张图处理两个平台：初期入口较少，但平台分支会侵入节点和状态，BOSS 聊天状态无法表达 51job 投递结果。
3. 同一项目、独立流程图：共享经过验证的基础能力，隔离平台网页动作、结果判断和运行记录。用户已选择此方案。

## 第一版范围与设计默认值

以下为设计者建议，随本设计交用户确认，不冒充用户已经逐项指定：

- 新增 `python/jobpilot/platforms/job51/` 模块以及独立 `job51` CLI 入口；保留现有 BOSS 命令和模块位置。
- 支持 preview、run、resume、report。preview 不触发投递；resume 延续原批次计数，不重新获得 50 个名额。
- 首轮用固定关键词「Java后端开发」，深圳，主搜索结果列表；不采集侧栏推荐、不自动扩大城市或轮换关键词。
- 读取详情，要求职位确实属于 Java 后端开发；Java 全栈且明确包含 Java 后端职责可纳入。纯前端、测试、培训招生等不投。依据详情原文进行可解释筛选，含糊不清的岗位记为待核验。
- 不擅自沿用 BOSS 的 1–3 年、3–5 年经验筛选；第一版不设置新的薪资、学历、公司性质、外包、休息制度硬门槛。只展示页面已知条件，不引入 LLM 匹配打分作为必经节点。
- 从列表进入职位详情后识别投递入口；若详情没有入口，可在返回并确认同一岗位身份后使用该岗位卡片的投递按钮。两个位置的入口仍属于同一项投递，不能各提交一次。确认两处均无投递入口时跳过。
- 使用当前账号已有、页面明确展示的 Java 求职简历，不上传本地文件或修改在线简历。如果页面出现多份简历且默认项无法明确识别、要求额外问答或新增附件，则暂停并报告具体缺项，不替用户选择未知材料或编造回答。
- 浏览器控制沿用项目现有扩展与本地桥的技术路线，新增 51job 独立适配模块及协议。是否单独打包扩展由实施者根据现有绑定代码决定；不得复用 BOSS 会话绑定去操作 51job。域名权限仅加入实际核验的 51job 页面来源。

## 图与工具职责

LangGraph 负责步骤、分支、循环、暂停和恢复；网页适配器负责读取可见页面、定位控件、点击与提取结果。不能把所有操作塞进一个节点再称为完整流程编排。

主要节点：

| 节点 | 职责与出口 |
| --- | --- |
| preflight | 核对 51job 账号、网页绑定、运行范围、批次锁与未决动作；登录失效暂停 |
| search | 设置深圳和固定关键词，验证搜索条件实际生效 |
| collect / select | 读取主列表、解析岗位身份、去重；选下一岗位或推进列表 |
| inspect_job | 进入详情，核对公司、职位、地点、岗位职责、投递状态与入口 |
| prepare_application | 定位已有简历与已知确认步骤；资料不明确则暂停 |
| reserve_application | 在可能提交的首次点击前，原子占用名额并写入动作意图 |
| apply | 调用专用投递动作；页面如果先出现弹窗，记录阶段，不宣称已投递 |
| confirm_application | 仅在页面明确需要且与同一岗位、已确认简历一致时提交确认；沿用同一名额 |
| verify_application | 根据同一岗位的成功提示、已投递状态或投递记录核验结果 |
| restore / advance | 返回并验证原搜索条件，继续候选或分页；状态变化无法确认则暂停 |
| recover_application | 先读取原动作及网页证据，恢复未决项；不盲目重放 apply/confirm |
| summarize | 输出成功、失败、未知、跳过、预算占用及停止原因 |

若简历选择只在点击投递后出现，prepare_application 先完成可见信息检查，apply 后由 confirm_application 核验选择。未知简历导致暂停，已预留名额保留。

仅确认成功、明确失败或确定跳过后，才进入下一岗位。投递结果未知时暂停整个批次，防止剩余动作掩盖未决结果。

## 50 个上限与恢复语义

将「最多投递 50 个」保守落实为本批次最多对 50 个不同岗位发起投递尝试；不承诺 50 个成功。

- 阅读、筛选、已投递和无入口跳过不占名额。
- 首次可能产生投递的动作前原子预留名额；每岗位一份名额，后续确认弹窗不重复计数。
- 已派发后失败或结果未知仍占名额，不自动补投到 50 个成功。
- 中断恢复、CLI 重启、checkpoint 回放不重置名额。批次锁阻止同账号同批次并发提交。
- 对副作用保持独立动作账本；checkpoint 恢复本身不构成网站投递幂等保证。
- 结果未知的原动作先查证；无法查证则暂停，不因为超时再次点击。新批次也跳过已成功项并阻塞同账号未决项。

## 状态、记录与数据隔离

核心身份包含 platform=`51job`、account_id、job_id（或规范化岗位URL）、batch_id、attempt_id、request_id。账号无法稳定识别时不得运行真实投递。

投递阶段至少区分 reserved、dispatched、awaiting_confirmation、confirmed、failed、uncertain；候选另有 skipped、needs_user_info。页面显示「已投递」但无法证明是本批次产生的，记历史跳过，不计本批成功。

新增 51job 专用表或独立数据库存放于 `data/`，截图与敏感页面证据按需放 `private/`。日志保存最小必要证据和本地时间，不收集无关聊天、联系方式或凭据。报告列出岗位、链接、结果、证据和原因。不提交私人材料、运行记录和账号数据。

同公司跨平台相似岗位可以提示，但不以公司名相同就自动判定同一岗位。BOSS 额度记录不影响 51job 预算，51job 结果不写成 BOSS 的已招呼。

## 完成标准

- 独立 LangGraph 图覆盖搜索到投递核验、返回、继续与恢复；只投递入口可达，无聊天动作。
- 可证明只处理深圳主搜索结果、岗位身份保持一致；职位关闭、已投递、无入口等明确跳过。
- 离线测试覆盖 50 上限、弹窗确认只占一个名额、恢复不重复提交、未知结果暂停、历史去重、侧栏排除、账号切换、列表返回与翻页失败。
- 现有 BOSS 相关回归检查通过；不能用 51job 改动改变 BOSS 既有授权和行为。
- 实站先验证预览，再在同一已授权批次中完成首项投递并核验；成功后才继续，仍共享 50 名额。登录、验证码或待补材料出现时按实际页面暂停。
- 离线测试通过不能写成真实投递成功；最终报告明确实际成功数与所有未完成项，不把上限写成执行结果。
