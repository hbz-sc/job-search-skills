# 方案 A：从当前岗位列表完成沟通循环

状态：用户已通过“实现方案A”批准实施；代码、回归测试、0.8.0部署与真实只读预览完成。按最新项目约定，本轮不自动发送招呼，真实发送及返回循环尚未验收。

Builder check：独立审查已完成，结论“nothing important left”。首次模板绑定、同批次预算、发送去重、未知结果暂停和原列表条件保持均已明确，无需用户补充技术细节。

## 目标与依据

用户要求从 BOSS 当前职业列表开始，逐个点击立即沟通，使用常用语第一条，确认发送后返回原列表并重复，最多150次招呼尝试。城市不限，但程序不应通过重新搜索改变用户当前选择。用户同时需要能说明问题的日志与 LangGraph 学习说明。

现有 preview 已能读到6个1–3年岗位和9个3–5年岗位，但它按设计跳过沟通。CLI 将所有节点都显示为沟通计数，导致搜索与常用语状态难以理解。现有 run 在列表启动会因缺少模板要求先到已有聊天，因此未满足列表直达沟通的目标。现有恢复通过搜索返回列表，也可能改变城市或其他筛选。

## Approaches

- A（用户选择）：接管当前已打开列表，保留页面条件，不重新点击搜索，完成沟通后返回原列表。最贴合用户操作，需增加列表快照、原列表恢复与首次模板绑定。
- B（未选择）：脚本重新搜索并恢复筛选后沟通。可从更多初始页面启动，但要处理站点搜索重置条件，增加城市变化风险。

## 使用方式与范围

提出独立入口 `jobpilot.cmd current-list run --max-contacts 150 --confirm-send`，避免把既有 preview 暗中变成发送命令。配套 `current-list preview`、`status`、`resume`；具体命令结构由实施计划统一，但必须清楚显示“真实沟通”或“只读预览”。既有 fixed-search 保留兼容。

启动必须在已登录的职位列表。程序记录当前城市、关键词、经验以及页面支持识别的其他筛选，不重新设置城市、关键词、经验、公司规模、求职类型。关键词或城市不限。沿用已确认的1–3年、3–5年岗位范围：两档同时按列表顺序处理，不分两次重新搜索；其他年限或年限无法确认的岗位跳过并说明。

用户目前已有的城市不限授权，并不等于可以由程序切换城市。若用户手动改变列表条件或网站改变它们，暂停并报告变化，不悄悄接受新列表为原列表。

不自动回复招聘方、不上传简历、不交换联系方式，不操作其他账号。只对去重后且符合年限的当前列表岗位执行新沟通。

## 完整流程与 LangGraph 映射

`load_config → inspect_current_list → collect_candidates → select_candidate → inspect_job → reserve_contact → open_chat → read_first_phrase → bind_or_check_phrase → send_phrase → inspect_result → restore_original_list → collect_candidates`

普通边连接顺序步骤；条件边控制以下分支：

- 已联系、重复、不符合经验或岗位失效：记录原因，返回列表处理下一条，不占用新沟通次数。
- 当前可见岗位处理完：在原列表滚动/翻页，再收集；不提交新搜索。
- 发送确认成功或明确失败：保存结果，再返回原列表。成功只根据可见消息证据记数。
- 结果未知、登录/验证、平台额度不足、接收人不明、原列表条件变化：暂停并保留现场，不自动重发。
- 150次已占额尝试、列表耗尽或有界翻页无新增：汇总并停止。150是上限，不保证150次成功。

State 包括 batch_id、mode、list_snapshot、current_job、candidates、seen_job_keys、template_hash、attempt_id、counts、last_action、stop_reason。页面对象不写入checkpoint；恢复重新观察页面。

## 原列表快照与返回

保存同一浏览器会话的标签、文档身份、受支持的 BOSS 职位页 URL、规范化业务查询参数、可见城市和筛选证据、已处理岗位键。记录原 URL 不代表允许调用者传入任意网址。

聊天若开在新标签，保留并激活原岗位标签；同标签跳转则优先回到观察过的原列表历史位置。必要的恢复只能由扩展使用本批启动时自己捕获的同站职位页目的地；MCP 不提供任意URL导航入口。返回后重新核对条件再继续，并按岗位键恢复遍历，不能仅用屏幕位置判断同一岗位。

一次批次最多50次列表推进，连续3次无新岗位停止；已处理岗位不因翻页/返回/重启重复联系。浏览器断开后显式 resume，在原授权目标核验后恢复；不承诺自动跨会话迁移。

## 首次常用语与权限分阶段

首次不要求用户先开已有聊天。先占用一次预算并点击立即沟通，进入已核对接收人的聊天，再只读第一条常用语。网站点击立即沟通可能自行生成招呼，因此点击前计入尝试数，即使后续读取失败也不退回预算。

协议不能简单删除原有模板 hash 检查。新增专用于 current-list 的协议（建议v4，避免改变v3语义），区分“已授权打开聊天/只读模板”和“已绑定模板可发送”：

1. 启动阶段允许读取列表、查看岗位、占额后打开一个聊天、只读常用语，不允许选择常用语或提交消息。
2. 首个聊天读出第一条模板后，通过专用绑定动作把该次观察的文本hash固定到当前批次和租约。桥与扩展均验证该观察属于当前接收人/请求；不能任意传一个hash授权发送。
3. 绑定在同一批次中完成，不重启预算、不重置去重或open_chat计数。后续每个聊天重新读取第一条并核对同一hash。
4. 第一条缺失或读取不明确时暂停；平台默认“我可以把我的简历发给您看看吗？”若不是可核验的保存常用语，不把它冒充第一条。出现模板变化暂停，不能自动替换。

第一条常用语点击后可能直接发送，也可能填入编辑框。根据页面结果决定是否点击发送，禁止一律再次点击发送。保留原请求ID、发送前消息基线摘要及确认凭据；未知结果仅查询与观察原操作，不重新派发。

## 日志与可读性

终端开始时明确模式、预算、当前关键词、城市证据、经验条件。每个节点显示“开始/完成/跳过/失败”和耗时，不把所有节点都打印成沟通次数。

独立计数：已读岗位、去重后候选、已跳过、沟通尝试、常用语读取成功、发送已确认、发送失败、待核验、返回列表完成。日志中的0要附计数含义；未执行写“未执行”，不要假装读取常用语成功。

JSONL结构化日志：本地时间、batch_id、node、tool、request_id、阶段、耗时、当前岗位键/公司岗位、页面身份、业务筛选前后变化、原始错误码、恢复建议。任意异常消息需清洗；不记录密钥、认证token、cookie、完整聊天记录。话术日志默认仅序号、长度和hash，不输出正文。URL只记录允许的业务路径与查询字段，不复制跟踪或认证参数。

日志先记录动作意图，再记录可观察结果。明确区分预检查、按钮点击、消息已提交、消息已确认，不能把点击成功当成发送成功。每次失败附本地日志与报告路径。

## 验收标准

真实发送验收与本地测试分别报告：只有可见成功证据才记为发送成功。未完成闭环时必须标明未完成，不使用“全流程已跑通”。
